# UI-Vertrag v1 (Backend und Control Center)

Ein Vertrag, zwei Seiten: **Strang A** (Autonomie und Agenten) liefert ein Backend, das ihn erfüllt; **Strang B** (Control Center) baut die Oberfläche dagegen und testet bis dahin mit dem Fake-Backend. Umsetzung: `src/jarvis/ui_contract/` (nur Standardbibliothek; einzige Ausnahme: `bus.py` schwärzt mit `jarvis.redaction`). Normativ ist der Code (`schema.py`); die JSON-Schemas für das Frontend liegen in `src/jarvis/ui_contract/schema/` und werden mit `python -m jarvis.ui_contract.schema` erzeugt (ein Test erkennt veraltete Dateien).

## Umschläge
Ereignis (Backend → Oberfläche): `{"v": "1.0", "seq": 12, "ts": "2026-11-02T10:00:00Z", "type": "chat", "data": {...}}`
Befehl (Oberfläche → Backend): `{"v": "1.0", "id": "c42", "type": "submit_text", "data": {"text": "..."}}`
Antwort auf jeden Befehl: ein `ack`-Ereignis `{"id": "c42", "ok": true|false, "code": "...", "message": "..."}`.
Alles ist streng: genau diese Felder, begrenzte Längen, geschlossene Typmengen, Version `1.x` (Hauptversion 1; eine andere wird abgelehnt). Steuerzeichen in Texten werden durch Leerzeichen ersetzt.

## Ereignisse
| Typ | Zweck | Wichtige Felder |
|---|---|---|
| `hello` | immer das erste Ereignis eines Schnappschusses | `contract`, `backend`, `capabilities`, `emergency` |
| `state` | Zustand der Oberfläche | `state`: ready, listening, processing, speaking, awaiting_confirmation, error, emergency |
| `chat` | Gesprächsverlauf | `sender` user/jarvis/system, `text` (höchstens 4000 Zeichen) |
| `activity` | Schnappschuss der laufenden Arbeit | `items` (kind, id, title, status, note, cancellable), `problems`, `inactive` |
| `task_update` | Änderung einer Aufgabe | `kind`, `id`, `status`, `detail` |
| `routing` | Wer bekommt die Aufgabe und warum (Agenten-Router) | `task_id`, `agent`, `source` llm/rules, `reason` |
| `result` | Ergebnis mit Belegen | `task_id`, `summary`, `artifacts` (name, kind, ref) |
| `confirmation_request` | Rückfrage der Berechtigungs-Engine | `request_id`, `tool`, `action`, `resource`, `level`, `reason`, `context`, `choices`, `timeout_s` |
| `confirmation_closed` | Rückfrage beendet | `outcome`: allow_once, allow_session, denied, timeout, cancelled |
| `emergency` | Notaus-Zustand | `engaged`, `reason`, `report` |
| `voice_level` | Mikrofonpegel für die Sprachvisualisierung | `level` 0..1, `active` |
| `error` | Fehler (nur Text, nie Inhalte) | `code`, `message` |
| `ack` | Antwort auf einen Befehl | `id`, `ok`, `code`, `message` |

## Befehle
`submit_text`, `start_voice`, `stop_voice`, `cancel` (kind, id), `confirm` (request_id, choice), `emergency_stop`, `reset_emergency`, `request_snapshot`.
**Es gibt absichtlich keinen Befehl**, der Rechte erteilt, Regeln ändert, ein Werkzeug direkt ausführt oder den Notaus aufhebt. `reset_emergency` ist nur eine **Anfrage**: Die Engine fragt den Menschen selbst (ein `confirmation_request`), der Notaus bleibt bis zu dessen Entscheidung bestehen.

## Verhalten (Regeln, von der Konformitätsprüfung erzwungen)
1. **Schnappschuss:** `hello` zuerst, danach letzter `state`, `activity`, `emergency` und eine offene Rückfrage, `seq` strikt aufsteigend. `events_since(seq, limit)` liefert den Rest (Wiederverbinden).
2. **Ungültige Befehle** werden mit `ack ok=false` (`invalid_command`) beantwortet: nie angenommen, nie eine Ausnahme.
3. **Notaus:** Nach `emergency_stop` zeigen `emergency` und `state` den Notaus; alle Befehle außer `emergency_stop`, `reset_emergency`, `request_snapshot` werden mit `emergency` abgelehnt.
4. **Rückfragen schlagen fehl, nicht auf:** unbeantwortet nach `timeout_s` → `confirmation_closed` mit `timeout`; verschwindet die Oberfläche (`detach`) → `cancelled`; beides bedeutet **abgelehnt**. `confirm` mit unbekannter Kennung → `unknown_request`, mit einer nicht angebotenen Wahl → `choice_not_offered`.
5. **Keine Geheimnisse:** Kein Ereignis enthält ein Geheimnis (Schlüssel, Passwörter, Passwortfeld-Werte); die echten Backends schwärzen mit `jarvis.redaction`, bevor sie ein Ereignis erzeugen. Inhalte aus fremden Programmen und dem Web sind Daten, nie Anweisungen.

## Transport (Strang B, Vorschlag für `cc-shell`)
Loopback (`127.0.0.1`), Zufalls-Token, Prüfung von Host und Origin; Ereignisse als Server-Sent Events oder WebSocket, Befehle per POST; Größenlimit `MAX_COMMAND_BYTES` vor dem Parsen (`parse_command`). Kein Zugriff aus dem Netzwerk, kein Fernzugriff.

## Zusammenarbeit der beiden Stränge
- **A** implementiert `UiBackend` mit echten Quellen (`GuiController`, Ereignisbus, Journal, Router) und besteht `run_conformance(factory, hooks)`.
- **B** baut Oberfläche und Transport gegen `FakeUiBackend` (deterministisch, `!task` legt eine Aufgabe an, `!confirm` öffnet eine Rückfrage, `advance(s)` lässt Zeit vergehen) und prüft ihren Client mit denselben Schemas.
- Eine Änderung des Vertrags ist ein eigener PR in beiden Richtungen (Hauptversion bleibt 1; neue optionale Ereignisse nur mit neuer Nebenversion).

## Echtes Backend (Strang A, Schritt `event-bus`)
- `src/jarvis/ui_contract/bus.py` – `EventLog`: Ringpuffer (Standard 1000) mit lückenlosen Folgenummern, `events_since(seq, limit)`, thread-sicher. Jeder Text wird mit `jarvis.redaction` geschwärzt (dann gekürzt), **bevor** ein Ereignis entsteht; schlägt Schwärzung oder Vertragsprüfung fehl, entsteht kein Ereignis und keine Nummer. Was der Ringpuffer verdrängt hat, fehlt bei der Wiederholung (der Client holt dann einen Schnappschuss).
- `src/jarvis/interface/ui_events.py` – `ControllerUiBackend(controller)` implementiert `UiBackend` über den `GuiController`: übersetzt dessen Ereignisse (Zustand, Chat, Aktivität, Notaus, Sprachmodus als `voice_level`) und bildet die Befehle **ausschließlich** auf vorhandene Controller-Methoden ab (`submit`, `start_voice`, `stop_voice`, `request_cancel`, `emergency_stop`, `reset_emergency`, `request_activity`); ein Strukturtest erzwingt das. Kein Zugriff auf Core, Werkzeuge oder PermissionEngine. `reset_emergency` stellt nur die Anfrage.
- Rückfragen: `adapter.confirmation_provider` (ein `ConfirmationProvider`) macht aus Anfragen der Engine `confirmation_request`-Ereignisse. Ohne Antwort nach `timeout_s`, bei `detach()`, beim Notaus und bei jedem Fehler gilt **abgelehnt** (`timeout` / `cancelled`). Der Adapter importiert `jarvis.permissions` nicht (Sicherheitstest `test_only_tools_bootstrap_and_cli_use_the_permission_package`); die spätere Verdrahtung reicht `ConfirmationChoice` als `choice_enum` herein. Nach `detach()` werden neue Fragen sofort abgelehnt, bis sich wieder ein Client meldet (`snapshot()` / `send()`).
- Der Adapter holt die Controller-Ereignisse selbst ab (`pump()`, auch bei `snapshot`/`events_since`/`send`); er ersetzt damit das Tk-Fenster als Abnehmer und setzt `set_confirmation_denier`. Ein Controller hat genau einen Abnehmer.
- **Abweichung vom Fake, bewusst:** Beim Notaus bleibt `confirm` gesperrt, **außer** für die Frage der Engine „Notaus aufheben?“ (`tool=jarvis`, `action=emergency_reset`); nur so kann der Mensch sie über die Oberfläche beantworten. `deny`, Zeitüberschreitung und Trennung lassen den Notaus bestehen. Der Fake sperrt `confirm` beim Notaus ausnahmslos – das Vertragsdokument sollte das klären (eigener PR, Besitzerentscheidung).
- **Verdrahtet (Schritt `assistant-e2e`):** `bootstrap.py` baut den Adapter nur mit `assistant.enabled` (Standard aus) und setzt ihn als Bestätigungs-Provider der Engine (außer `security.confirmation = "deny"`); zusätzlich Notaus-Stopper `assistant`. Der Adapter bekommt `add_pump_hook`, `publish`, `publish_finished` und `last_seq`: `interface/assistant.py` veröffentlicht darüber `routing`, `task_update` und `result` und schreibt das Journal. Es gibt weiterhin keinen Transport; nichts startet von selbst. `submit_text` verhält sich wie die Eingabezeile der GUI (auch `/…`-Befehle des Controllers).

## Control-Center-Shell (Strang B, Schritt `cc-shell`)
- `src/jarvis/control_center/server.py` – `ControlCenterServer(backend)`: `ThreadingHTTPServer` nur auf `127.0.0.1` (jeder andere Host wird abgelehnt), Zufalls-Token (`secrets`, Vergleich zeitkonstant; per `?t=` oder Header `X-JARVIS-Token`), Pruefung von `Host` (`127.0.0.1:<port>`/`localhost:<port>`) und `Origin` (bei POST Pflicht), keine CORS-Header. Reihenfolge: Host → Origin → Token → Route; ohne gueltiges Token liefert jeder Pfad 401 ohne Inhalt.
- Ereignisse: `GET /events` (Server-Sent Events; Schnappschuss, danach `events_since`; Wiederverbinden per `?since=` oder `Last-Event-ID`; hoechstens 4 Clients). Verlaesst der letzte Client den Strom, ruft der Server `backend.detach()` (offene Rueckfragen gelten als abgelehnt).
- Befehle: `POST /command` (`application/json`, `Content-Length` Pflicht, hoechstens `MAX_COMMAND_BYTES` vor dem Lesen, dann `parse_command`); ungueltige Befehle erreichen das Backend nie und werden mit `ack ok=false` (`invalid_command`, HTTP 400) beantwortet.
- Weboberflaeche `web/` (`index.html`, `app.js`, `styles.css`): nur lokale Dateien, CSP `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'` (kein Inline-Code), kein `innerHTML`, kein Fremdcode, Canvas 2D. **Premium V2:** Start im Orb-Modus, der Knopf wechselt jederzeit zum Dashboard und zurueck; der Modus ist reine lokale Anzeige (setzt nur ein Attribut, sendet nichts, beruehrt X0, PermissionEngine und Notaus nicht). Der Notaus-Knopf (`emergency_stop`) ist in beiden Modi sichtbar. 
- **Rueckfrage-Dialog (Schritt `cc-confirmation`):** `confirmation_request` oeffnet einen modalen Dialog ausserhalb der Orb-/Dashboard-Ansichten (in jedem UI-Modus gleich) mit Werkzeug, Aktion, Ressource, Stufe, Grund, Kontext, Wahlmoeglichkeiten und Restzeit. Standard ist **Ablehnen**: die Schaltflaeche steht zuerst und hat den Fokus, Escape lehnt ab, Enter bestaetigt nie. Es gibt nur Schaltflaechen fuer Wahlmoeglichkeiten, die die Anfrage anbietet (keine Sitzungsfreigabe ohne Angebot); gesendet wird ausschliesslich `confirm` mit `request_id` und `choice`. Mehrere offene Anfragen werden nacheinander gezeigt, keine bleibt verdeckt. Zeitablauf (`timeout`), Schliessen des Fensters oder Verbindungsverlust (der Server ruft `detach()` -> `cancelled`) gelten als abgelehnt; bei Verbindungsverlust zeigt die Oberflaeche nichts Beantwortbares mehr. Der Notaus-Knopf liegt in der Leiste ueber dem Dialog (hoeherer `z-index`, nie `inert`), ist in beiden Modi und bei offenem Dialog sichtbar und sendet `emergency_stop` ohne Rueckfrage. Der Dialog beruehrt X0, PermissionEngine und Notaus nicht; die Entscheidung trifft allein die Engine.
- Start nur auf ausdruecklichen Befehl: `jarvis-cc [--open]` bzw. `python -m jarvis.control_center [--open]` (Browser nur mit `--open`); seit `cc-backend-binding` gegen das echte Backend (siehe unten). Nichts importiert das Paket, `bootstrap.py` startet es nie. Keine neue Abhaengigkeit (`dependencies = []`; kein Extra `cc`, da nur die Stdlib-Stufe freigegeben ist). Native Fenster/Mini-Overlay, Three.js und pywebview sind **nicht** freigegeben.

## Dashboard (Strang B, Schritt `cc-dashboard`)
- Dashboard im Premium-V2-Layout: **Agenten links, Kugel mittig, Aufgaben/Details/Ergebnisse/Rueckfrage rechts** (schmale Fenster: untereinander). Es zeigt ausschliesslich Vertragsdaten: `activity` (Liste), `task_update` (Status, Detail), `routing` (Agent, Quelle llm/rules, Grund; die Agentenliste wird daraus abgeleitet), `result` (Zusammenfassung und Belege). Alle Texte werden mit `textContent` gesetzt, nie als HTML; Belege (`ref`) sind reiner Text, nie ein Link.
- **Abbrechen** sendet nur `cancel` (`kind`, `id`) und zeigt die echte Antwort des Backends: `ok` mit `cancel_requested` -> „Abbruch angefordert“ (der Abbruch laeuft noch; `task_update` mit `CANCELLED` bestaetigt ihn), sonst `ok` -> „abgebrochen“, `ok=false` -> „abgelehnt“ mit Code und Meldung. Der Knopf erscheint nur bei `cancellable` und nicht fuer beendete Arbeit.
- **Automatischer Wechsel in das Dashboard** (rein lokale Anzeige, wie der manuelle Wechsel): nur bei mindestens **drei** aktiven `activity`-Eintraegen der Art `plan` (belegbare geplante Schritte) **oder** mindestens **zwei** verschiedenen Agenten aus `routing` zu noch aktiven Aufgaben. Nach einer manuellen Umschaltung wechselt die Oberflaeche nie mehr selbst; zurueck zum Orb wechselt nur der Mensch.
- **Datenluecke (X0):** Der Vertrag enthaelt keine verlaesslichen X0-Daten zur Komplexitaet einer Anfrage (kein Feld fuer Schaetzung, Schrittzahl vor dem Plan oder X0-Einstufung). Die Oberflaeche leitet deshalb nichts aus Chat-Text, Titel oder Laenge ab und wechselt ohne die oben genannten Belege nicht. Soll X0 kuenftig den Wechsel steuern, braucht der Vertrag ein eigenes Feld (eigener PR in beiden Richtungen). Die manuelle Umschaltung bleibt immer moeglich.
- Das Dashboard beruehrt X0, PermissionEngine und Notaus nicht; Befehle bleiben `cancel`, `confirm`, `emergency_stop`, `submit_text`. Verdrahtet mit `cc-backend-binding` (siehe unten).

## Animierter Kern (Strang B, Schritt `cc-ai-core`)
- **Technik:** Canvas 2D (Three.js ist nicht freigegeben) - dokumentierter 2D-Ersatz fuer die 3D-Kugel: Pseudo-3D-Kugel mit Lichtreflex, drehenden Meridianen, geneigten Ringen mit Energieteilchen (Vorder-/Rueckseite) und Leuchten. Keine externe Ressource, kein Inline-Code.
- **Tabelle `web/core_states.json`:** Zustand -> Aussehen (`label`, `color`, `glow`, `pulse_hz`, `pulse_amp`, `spin`, `rings`, `particles`, `level_gain`, `flash_hz`) fuer genau die sieben Zustaende des Vertrags plus `neutral`. `tests/test_control_center_core.py` prueft Vollstaendigkeit, Wertegrenzen und Farben; `app.js` klemmt zusaetzlich auf dieselben Grenzen und faellt bei fehlender/ungueltiger Tabelle auf neutral zurueck. Der Server liefert die Datei nur mit Token (`GET /core_states.json`).
- **Farben:** ready gruen, listening blau, processing violett, speaking tuerkis, awaiting_confirmation goldgelb, error rot, emergency kraeftigeres Rot mit Blinken (nur im vollen Modus); beim Notaus faerbt sich zusaetzlich Leiste, Rand und Beschriftung rot. Der Notaus-Knopf bleibt in jedem Modus sichtbar.
- **Nur Backend-Zustaende:** Beim Start und nach Verbindungsverlust gilt `data-state="none"` (neutral grau, "kein Zustand gemeldet"). Gezeigt wird nur, was ein `state`-Ereignis oder ein `emergency`-Ereignis mit `engaged=true` meldet; unbekannte Werte werden nicht gezeigt (kein erfundenes `error`/`ready`). Hebt das Backend den Notaus auf, bleibt die Anzeige bis zum naechsten `state`-Ereignis. Die Bewegung (Pulsieren, Drehen) ist reine Zierde des gemeldeten Zustands; nur `voice_level` bewegt die Groesse, und nur bei listening/speaking.
- **Effekte:** Auswahl "voll / reduziert / aus" in der Leiste (rein lokal, sendet nichts, speichert nichts). `prefers-reduced-motion: reduce` erzwingt "aus" (ein stehendes Bild, nicht uebersteuerbar). Bei geringer Leistung (Bildzeit im Mittel > 45 ms im vollen, > 120 ms im reduzierten Modus, 30 langsame Bilder) wird automatisch eine Stufe reduziert und ein Hinweis gezeigt; es wird nie selbst erhoeht, der Mensch kann zuruecksetzen. "reduziert" = Kugel und Ringe, ca. 20 Bilder/s, ohne Teilchen und Meridiane.
- Der Kern beruehrt X0, PermissionEngine und Notaus nicht; es kommen keine neuen Befehle hinzu. Verdrahtet mit `cc-backend-binding`. Echte Browser-/GPU-Messung der Leistung und der Windows-Nachweis stehen aus.

## Sprachanzeige (Strang B, Schritt `cc-voice-viz`)
- **Leiste „Sprache“** (`#voice-bar`, in Orb- und Dashboard-Modus gleich): Knöpfe „Sprache starten“ (`start_voice`) und „Sprache beenden“ (`stop_voice`), Anzeige „Mikrofon: an/aus/unbekannt“, „Sprachzustand“ (listening = „hoert zu“, processing = „verarbeitet“, speaking = „spricht“; andere Zustände zeigen „-“), Pegelbalken (`<meter>`), Pegeltext („Pegel 42 %“) und eine Wellen-Canvas.
- **Mikrofon nur auf Knopfdruck:** `start_voice` wird in `app.js` genau an einer Stelle gesendet, im Klick-Handler von „Sprache starten“ (ein Test erzwingt das); weder `voice_level`, `state`, Moduswechsel noch Effekte senden einen Befehl. Das Mikrofon gehört dem Backend; die Seite greift nie darauf zu. Der Server sendet zusätzlich `Permissions-Policy: microphone=(), camera=(), geolocation=()`.
- **Keine Audiodaten im Frontend:** Asset-Prüfung (Test) verbietet Audio-/Medien-APIs (`getUserMedia`, `AudioContext`, `MediaRecorder`, `SpeechRecognition`, `Blob`, typisierte Arrays …), Medienelemente und Audio-Dateitypen in `web/`. Die Seite sieht nur den Zahlenwert `level` (0..1) und `active` aus `voice_level`.
- **Nur echte Ereignisse:** Pegel, Welle und Mikrofonstatus ändern sich nur durch `voice_level` (`active=false` erzwingt Pegel 0); der Zustand kommt nur aus `state`. Die Welle (Verlauf der letzten 48 Pegel) wird nur bei einem Ereignis gezeichnet, nie durch Zeitablauf, ohne Zufall, ohne Zeitgeber. Der Kern (`cc-ai-core`) bezieht sein Pulsieren aus demselben `level` und nur bei den Zuständen mit `level_gain` > 0. Bei Verbindungsverlust gilt Mikrofon „unbekannt“, Pegel 0. Meldet das Backend den Notaus, zeigt die Seite „Mikrofon: aus“ und sperrt „Sprache starten“ (das Backend lehnt den Befehl ohnehin ab).
- **Effekte aus / `prefers-reduced-motion`:** Text, Mikrofonstatus, Sprachzustand und Pegelbalken bleiben vollständig lesbar; die Welle schrumpft dann auf einen ruhigen Balken des aktuellen Pegels (ohne Verlauf).
- Keine neuen Befehle, keine Berührung von X0, PermissionEngine und Notaus. Verdrahtet mit `cc-backend-binding`; das Fake-Backend liefert nur Pegel 0, echte Pegelwerte und der Windows-Nachweis stehen aus.

## Anbindung an das echte Backend (Strang B, Schritt `cc-backend-binding`)
- **Startbefehl:** `jarvis-cc` (`pyproject`-Skript auf `jarvis.control_center.launcher:main`; gleichwertig `python -m jarvis.control_center`), Optionen `-c <toml>` und `--open`. Nichts startet von selbst: weder der Import noch `build_core`/`bootstrap.py`.
- **Einstellung `control_center.enabled`** (`src/jarvis/config.py`, Standard **false**, `JARVIS_CONTROL_CENTER_ENABLED`; nicht in `config/jarvis.toml`). Ohne sie bricht `jarvis-cc` vor dem Aufbau mit Fehlercode 2 ab. Es gibt keine Einstellung fuer Host oder Port: der Server lauscht ausschliesslich auf `127.0.0.1` (Zufallsport, Zufalls-Token, Host-/Origin-Pruefung wie in `cc-shell`).
- **Backend:** `core.subsystems["assistant"].ui` (`ControllerUiBackend`, Ablauf aus `assistant-e2e`). Braucht `assistant.enabled` und `agents.enabled`; fehlt es, bricht der Start ab (Fehlercode 2), es gibt **keinen Rueckfall auf das Fake-Backend**. `FakeUiBackend` wird nur in Tests verwendet (ein Test erzwingt, dass `control_center/` es nicht enthaelt).
- **Kein zweiter Berechtigungsweg, keine X0-Aenderung:** der Launcher importiert weder `jarvis.permissions` noch `jarvis.tools`, ruft kein Werkzeug auf und setzt keinen Provider; er reicht nur Vertragsbefehle an den Adapter weiter. `emergency_stop` loest den echten Notaus der Engine aus (Test), `reset_emergency` bleibt eine Anfrage, Rueckfragen beantwortet allein die Engine (Zeitablauf, `detach`, Notaus = abgelehnt).
- Tests: `tests/test_control_center_binding.py` (`run_conformance` gegen das echte Backend mit Rueckfrage- und Zeitablauf-Hilfen, Notaus-Knopf -> echte Engine, Standard aus, nur Loopback, Strukturtests). Echte Browser-/Windows-Pruefung (`cc-windows-start`, `cc-windows-smoke`) steht aus.
